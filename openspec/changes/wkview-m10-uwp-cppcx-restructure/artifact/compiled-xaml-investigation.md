# Compiled-XAML investigation (SDK 10.0.19041.0)

**Current result:** the durable repository host in `Tools/uwp/CXCompiledProbe`
builds via `build-arm32-cx-compiled-probe.ps1` and v6 passes compiled construction,
binding, inherited QI, actual measured layout, remove/reinsert and 32 weak-reference
final-release checks on the phone. `compiled-xaml-lumia-v6.txt` records the result.
Tasks 2.5 and 2.6 are complete; the owner supplied the v6 PASS-screen photo. The
sections below preserve the experimental steps that led to this recipe.

Status: compiled-XAML pass 1 and pass 2 now succeed in an isolated ARM32 C++
project target reproduction. The compiler emits XBF, page headers and the
generated metadata provider for the custom probe. Full project/package build and
phone execution remain unverified; tasks 2.5/2.6 remain open.

## Environment

- MSBuild 17.14.60
- Windows SDK 10.0.19041.0 XAML compiler / `Microsoft.Windows.UI.Xaml.Common.targets`
- MSVC 14.44.35207 ARM32 `/ZW`
- Device runtime proof remains package 1.0.0.27 in `xaml-binding-lumia-v27.txt`.

## Reproduction and findings

1. A minimal plain-XAML page compiles in XAML pass 1 after giving `CompileXaml`
   the SDK union WinMDs and UWP `mscorlib.dll`. An initial invocation using only
   the SDK union metadata fails `WMC9999` with `MsCorLib.dll not found`.
2. Pass 1 of a page with `x:Class="CxCompileProbe.CustomPage"` and
   `using:WebKitProbe` succeeds when given the ARM `/ZW` component WinMD produced
   by MSVC `link.exe /WINMD:ONLY`. It emits `CustomPage.g.h`,
   `XamlTypeInfo.Impl.g.cpp`, and `XamlLibMetadataProvider.g.cpp`; the page header
   declares the generated `WebKitProbe::XamlProbe` member. Thus the component
   metadata generated by MSVC is a better XAML compiler reference than the
   stand-alone MIDLRT WinMD previously tried.
3. The first SDK-target pass-2 attempts returned `WMC9999` from
   `AllLocalXamlHeaderFiles`. The test project passed no generated page header in
   `ClIncludeFiles`. Adding `CustomPage.g.h` as a `ClInclude` input resolves this
   exception. The control-only page additionally needs a normal project header
   in `ClInclude`.
4. With the page header supplied, the SDK `MarkupCompilePass1` and
   `MarkupCompilePass2` targets both succeed for plain XAML and the custom probe
   XAML. For the custom page, pass 2 emits `CustomPage.xbf` and
   `XamlTypeInfo.g.cpp`. The latter names `WebKitProbe.XamlProbe`, references its
   activator, and generates both read and write accessors for `ProbeText`. The
   generated `CustomPage.g.hpp` connects the page to the probe as well.
5. The generated page/type-info/provider C++ sources compile for ARM32 when the
   app compilation force-imports the component WinMD with `/FU`. The app-side
   objects link with `/WINMD:ONLY` to `CxCompileProbe.winmd`; inspecting the
   output confirms `CxCompileProbe.CustomPage` and the generated metadata
   provider are present. The linker reports duplicate generated connector
   methods and succeeds under `/FORCE:MULTIPLE`, matching the host's existing
   C++/CX link behavior. This is an isolated generated-code/WinMD check, not a
   complete executable or package.
6. A full component/app link, signed package and phone execution of compiled
   XAML have not yet been performed. Source generation and app WinMD evidence do
   not replace tasks 2.5/2.6 acceptance.

## Compiled-host device follow-up

- A separate generated C++/CX app now builds as an ARMNT AppContainer executable
  with an app WinMD, generated App/Page XBF files and a PRI. App/page/generated
  provider objects link without duplicate-method suppression after keeping the
  generated page implementation in its code-behind translation unit only.
- Package `WebKitProbe.XamlCompiledHost_1.0.0.1_arm__2932e6rj4m41p` installed but
  failed launch (HTTP 500, RPC_S_CALL_FAILED). Its dump recorded
  `0x80073B1F`, `ERROR_MRM_MAP_NOT_FOUND`. Its primary PRI map was named after the
  app namespace rather than the package identity.
- Version `1.0.0.2` changes the authored namespace to `CXCompileProbe` and the
  primary PRI map to `WebKitProbe.XamlCompiledHost`. It builds/signs/installs,
  but launch still returns RPC_S_CALL_FAILED. The v2 dump
  `XamlCompiledProbeHost.exe.5784.dmp` contains `0xC000027B` (stowed exception)
  at `Windows.UI.Xaml.dll+0x7F0713`; this is not proof of the underlying HRESULT.
  The dump contains the `CXCompileProbe/CustomPage.xbf` path. Compiled-page
  construction and binding remain unproven.
- Version `1.0.0.3` adds launch-stage logging and catches Platform exceptions
  around page construction to record the actual HRESULT/message in
  `LocalState/compiled-xaml-result.txt`. Build, packaging and signing succeed;
  Device Portal accepted the upload (HTTP 202), then timed out twice while
  polling deployment state. Installation completion and launch are pending.
- Current experimental build/source files remain under the temporary
  `opencode/xaml-compile-probe` directory; the experiment is not yet a durable
  checked-in project/recipe. The active temporary build script is `build-v2.ps1`
  (currently builds v3), with output `XamlCompiledProbe-v3-arm.appx`.
- The generated app imports `XamlProbeCX.winmd`, matching the MSVC-generated
  component metadata used by the XAML compiler. The working runtime v27 used
  MIDL-generated `XamlProbe.winmd`; these have different default interfaces and
  property metadata. Only the selected CX WinMD is staged in the compiled
  experimental package. Runtime activation must still be verified.

### V4 device result

V3 subsequently installed/launched and recorded `0x802B000A`, "Cannot create
instance of type 'WebKitProbe.XamlProbe'". Its manifest lacked the DLL's WinRT
in-process activation registration. V4 adds
`windows.activatableClass.inProcessServer`, registering `WebKitProbe.XamlProbe`
to `XamlProbeComponent.dll` with threading model `both`. With the same generated
executable/XBF payload, the freshly launched v4 package records `result=PASS`
and `bound=Compiled binding value`. See `compiled-xaml-lumia-v4.txt`.
