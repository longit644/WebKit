# M10 section 8: Windows Phone Edge-style chrome

## Owner requirements

The owner requested Microsoft Edge's Windows Phone design language: three persistent/expanded layers, system light/dark themes, no tabs, full visible-width expansion in portrait, half visible-width expansion aligned right in landscape, and an icon accompanying every secondary-menu label. The layers from bottom to top are the address bar, the expanded primary icon-and-label action strip, and the secondary action list. The address bar remains visible as the two upper layers open or close. The latest reference also highlights a vertical splitter between the compact address field and the three-dot button. When the address is focused, the editor expands across the bar, the side controls and splitter disappear, and the document dims. Owner screenshots are the visual reference; compile-only checks do not establish visual parity.

## References reviewed

- [UWP AppBar](https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.controls.appbar?view=winrt-15063): IsOpen, light dismissal, IsSticky, styling/templates; Microsoft recommends CommandBar for new Windows 10 apps. LightDismissOverlayMode was added in SDK 14393, before the phone's minimum 15063 target.
- [UWP CommandBar](https://learn.microsoft.com/en-us/uwp/api/windows.ui.xaml.controls.commandbar?view=winrt-15063): content, ellipsis, primary commands, secondary overflow; expansion reveals primary labels and opens secondary commands. Opening/closing must not change surrounding content layout.
- Installed Windows SDK 10.0.19041.0 `Generic/generic.xaml`: ControlContentThemeFontSize is 14, compact app-bar height is 40; AppBarButton labels are 12 and native overflow icons are 16. AppBarBackground resolves to the theme's ChromeMedium brush and disabled AppBarButton backgrounds are transparent. These are design/reference resources, not a claim that every 19041 template detail exists unchanged on Mobile 15254.

## Implementation and revisions

V4 established bottom chrome and one safe-area owner, but its context popup did not match the requested app-bar expansion. V5 replaced it with a docked animated icon/text panel and was installed (`Code=0`, `Success=true`) and launched (HTTP 200); the owner then rejected its large rows, gray disabled-background blocks, focus outline, and missing primary-action layer.

V6 retains the MVVM state and dismissal protocol and adopts the three-layer layout. Native AppBarButton controls provide the primary icons and labels below. Secondary rows use a custom Button template built from app-bar state resources: muted disabled foreground, transparent disabled surface, and no persistent focus rectangle. A neutral half-opacity document scrim is visible behind expansion. ThemeResource brushes supply the darker address/action band and secondary-menu surface. The browser's blank document canvas is white, consistent with default page rendering, while application chrome inherits the system theme. There are no new feature claims from the action-strip presentation: the existing browser commands and their availability remain authoritative.

The whole expanded panel animates above the unchanged 48-DIP address row; scroll height subtracts the primary strip so it remains visible in short landscape layouts. Root clipping prevents the slide from drawing over the system navigation bar. The ViewModel owns IsMenuOpen and toggle/close commands; view code owns animation, geometry, and focus. Repeated transitions invalidate old completion callbacks, and system Back dismisses expansion before navigating history.

The compact bar now has a 1-DIP system-themed splitter at the address/dots boundary. Address focus enters MVVM editing state: the chrome height becomes 44 DIP, the editor spans the three columns with 4-DIP side margins and 14-DIP text, and Reload, dots, and splitter collapse. A neutral half-opacity scrim dims the document without covering the bar. Outside tap, Escape, system Back, and keyboard dismissal restore the latest committed address; Enter submits through the existing policy and restores compact chrome. Source changes during editing update the cancellation target without overwriting the draft.

The phone's docked InputPane rectangle is included in safe-area margin calculation. The geometry helper treats its rectangle as window-local, combines keyboard and navigation insets with `max` rather than addition, and avoids applying the inset twice when `VisibleBounds` already ends at the keyboard. The page asks the OS not to pan the focused control, preserving a full-window Frame/Page while keeping the shell above the keyboard.

The owner's v7 screenshot comparison found that address text was not vertically centered. The follow-up explicitly sets `AddressBox.VerticalContentAlignment="Center"` in both compact and editing states. The optional base diagnostic now asserts the centered alignment, so a new package report verifies the property along with the existing geometry checks.
