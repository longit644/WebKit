## Resolved this session

### Fixture marker probes were reading the document too early (M9 4.2 evidence)

Root cause: `index.html` has a **blocking** `<script src="assets/first.js">` in `<head>`. The HTML
parser must wait for it before constructing `<body>`. `EmptyFrameLoaderClient::finishedLoading`
fires when the main document's network transfer completes, at which point `document->body()` is
still null, so `bodyText()` returned an empty string and all six probes reported false zeros
(`document-text-length: 0x0` while `document-bytes-total: 0x3d0` had been parsed).

Proof it was systematic rather than a race: `dispatchDidFinishLoad` already did
`getElementById("next")` plus a real hit test and got a 36-char link URL
(`link-center-url-length: 0x24`) on the same document.

Fix in `Source/WebCore/platform/uwp/PageUWP.cpp`:
- Moved probes from `finishedLoading` to `dispatchDidFinishLoad`.
- Added a settle chain at 300ms / 1200ms / 3000ms, because `load` does not wait for the two
  chained cookie fetches. `scheduleSettleProbe()` uses `RunLoop::currentSingleton()` +
  `dispatchAfter(Seconds, ...)`; this tree has **no** `RunLoop::current()` and **no** `callAfter`.
- Added `PageHostUWP::loadGeneration`, bumped per provisional load, so probes from a replaced
  document are dropped rather than reported into the new page.
- Removed the now-unused `bodyText()` static and the duplicate include.

v1.0.0.59 result (all five pass, and they discriminate):

| marker | at load | at settle |
|---|---|---|
| css-heading | 1 | 1 |
| script-order | 1 | 1 |
| fetch | 1 | 1 |
| xhr | 1 | 1 |
| cookie-pass | 0 | **1** |
| cookie-fail | 0 | 0 |

`cookie-pass` flipping `0` -> `1` proves the old harness was hiding a real result. `cookie-fail: 0`
is now meaningful; previously a broken cookie would have looked identical to a working one.

### Images were never requested (M9 4.2)

Root cause: `Settings::loadsImagesAutomatically()` defaults to **false for WebCore-only builds**
(`Source/WTF/Scripts/Preferences/UnifiedWebPreferences.yaml:5160-5166` sets `WebKitLegacy: true`,
`WebKit: true`, `WebCore: false`; materialized in the generated `Settings.cpp`). The port links
WebCore only and never opted in.

Chain: `FrameLoader.cpp:863` -> `CachedResourceLoader::setAutoLoadImages(false)` ->
`CachedImage.cpp:100-103` takes `setLoading(false)` and never calls `CachedResource::load()`, so no
`SubresourceLoader` is created and `LoaderStrategyUWP::loadResource` is never reached. This is a
silent no-op: no HTTP request **and** no `error` event on the `<img>`. CSS/JS/font/fetch/XHR are
unaffected because they call `CachedResource::load` directly and never hit the `CachedImage`
override.

Fix: added `setLoadsImagesAutomatically(true)` + `setImagesEnabled(true)` in both
`PageUWP.cpp` (~line 305) and `FirstPageUWP.cpp` (~line 168).

## OPEN BUG: crash at PNG decode (blocks image rendering)

### Observed

v1.0.0.60/61, immediately after the 73 image bytes arrive:

```
uwp-load-data: http://192.168.1.69:8000/assets/image.png: 0x49
native-fault-code: 0xc0000028
native-fault-address: 0x77109ce3
native-fault-module: C:\windows\SYSTEM32\ntdll.dll   (base 0x77050000, rva 0xb9ce3)
```

`0xc0000028` = `STATUS_FLOAT_INVALID_OPERATION`, raised in ntdll's FPU exception dispatcher.
This is the only new fault code; there is no `uwp-load-complete` for the image.

### Evidence gathered

- `libpng16.dll` imports both `longjmp` (ordinal 57) and `__intrinsic_setjmp` (ordinal 29) from
  the ARM store CRT. It also imports `floor`, `pow`, `modf`, `frexp`, `atof` - real FP use.
- `Source/WebCore/platform/image-decoders/png/PNGImageDecoder.cpp` wraps every libpng entry point
  in `setjmp`/`longjmp`: lines 179, 316, 330, 462, 483, 731, 867, 872, 885, 994, 1023.
- `z.dll` does **not** import `longjmp` - consistent with inflate working and only PNG crashing.
- Our own codegen is correct: `clang-cl --target=armv7-unknown-windows-msvc` emits proper AAPCS
  hard-float (`vadd.f64 d0, d16, d17`, FP args in `d0`/`d1`). So it is **not** an ABI mismatch in
  WebKit's own code.
- This is first-ever execution of the libpng path on this target: logs `device-1.0.0.42` through
  `.48` contain no `image.png` request at all.
- `Tools/uwp/FpuProbe` (new, this session) isolates it with no WebCore/XAML/libpng. v1.0.0.2 log:

```
probe-baseline-multiply:    0x1f40     (2.0*4.0*1000 = 8000, plain FP works)
probe-fpscr-before-setjmp:  0x0
probe-fpscr-traps-enabled:  0x0        (still zero AFTER writing 0x1f00)
<log ends>                              (expected probe-fpscr-after-longjmp never appeared)
```

### What this rules out (my own earlier hypothesis, now dead)

FPSCR trap-enable bits (IDE/IXE/UFE/OFE/DZE/IOE, mask `0x1f00`) are **privileged on ARM**. User-mode
code can read but not set them - the writeback read `0`. So "longjmp restores corrupt trap-enable
bits that then trap the next FP op" is **not** the mechanism. Do not re-derive it.

### Dump attribution (obtained 2026-10-03 evening, replaces the inference below)

`FpuProbeHost.exe.2020.dmp` (`WebKitWebView.FpuProbe_1.0.0.7`), parsed by hand
(`C:\Users\Longi\AppData\Local\Temp\opencode\FpuProbeHost.exe.2020.dmp`):

- Exception `0xc0000028`, thread 5752, fault address `0x77109ce3` = **ntdll+0xb9ce3
  — the identical offset MiniBrowser v61 logged**. Same fault, same place, with and
  without WebCore.
- Faulting stack carries `FpuProbeHost.exe+0x25ef`. Disassembly of the probe binary

  address.** No VCRUNTIME frames on the stack; fault PC is inside ntdll, LR=0.
- Fault-context FPSCR = `0x80000010`: N and IXC set, **trap-enable bits clear**.
  The FPSCR-trap theory is doubly dead - nothing enabled any trap, and the fault
  PC isn't even in FP code we own.

  Context pointer), so this is the genuine fault-time stack, not a stale one.

### Leading hypothesis (NOT yet proven)

A **bare `setjmp`/`longjmp` round trip faults on this target** - the v1.0.0.2 log stops right at the
`longjmp` call, with the FP baseline proven good and no WebCore involved. Leading reading: the ARM
store CRT's `longjmp` restores FPSCR and/or `d8`-`d15` from the wrong offset in `jmp_buf`, pulling
stack garbage into the FPU control register, which raises `0xc0000028` in ntdll.

This is inference from exception codes only. Two causes remain live and they imply different fixes:

1. **Store CRT's `longjmp` is broken** for ARM32 - much broader than PNG; every
   `setjmp`/`longjmp` in WebCore would be suspect.
2. **`libpng16.dll` and our code disagree about `jmp_buf` layout** - an ABI mismatch between the
   prebuilt libpng and this toolchain instead.

Distinguish these with a dump before building anything.

## Diagnostics defects found (worth fixing regardless)

1. **`DBG_PRINTEXCEPTION_C` noise.** v61 logged **99** `0x40010006` "fault" records. That code is
   raised by `OutputDebugStringA`, which `logResult` calls on *every* log line. They are our own
   logging, not assertions. I initially misread them as assert failures and drew a wrong conclusion
   from them. Filter this code out in the VEH before the next fault investigation.
2. **Silent `RELEASE_ASSERT`.** `Assertions.h:353-356` maps `CRASH()` to `std::abort()` when
   `DEVELOPER_MODE` is off, so live `RELEASE_ASSERT`s terminate invisibly in Release. Two dead ends
   this session came from that (`ImageBackingStore.h:215` in particular).
3. **`__RTDynamicCast` stub is unport-wide.** `Tools/uwp/toolchain/crrtti.c:16` returns 0
   unconditionally and its own comment admits only ICU call sites were audited. Every
   `dynamicDowncast` in WebCore lacking a `SPECIALIZE_TYPE_TRAITS` entry silently yields nullptr.
   That is a latent crash class across the whole port, well beyond images, and deserves its own
   audit.
4. `0xe06d7363` pairs at startup are C++ `std::bad_cast` (magic `0x19930520`), expected per
   `crrtti.c:7`. Not a crash.
